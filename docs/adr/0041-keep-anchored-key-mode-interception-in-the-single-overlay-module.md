# Keep anchored key-mode interception in the single overlay module

Bzs.Blazor keeps the per-key-mode `preventDefault` interception for anchored overlays in the single shared `BzsPopover.razor.js` module, dispatched by a four-branch switch on the `data-bzs-anchored-keys` attribute. A 2026-10-04 architecture review proposed replacing the switch with a keys-contract registry so each owner's JavaScript would register its own handler; the proposal was rejected on the deletion test. The intercepted surface is four small, mutually distinct `keydown` filters — menu trigger and menu-item arrows, context-menu arrows, listbox trigger and search-field keys, and the date-picker's day and period keys — and each branch's real behaviour (moving the active option) already lives in its owner's C# state machine. Introducing a registration seam would add cross-module handler registration, disposal-time unregistration, and synchronisation between the `data-bzs-anchored-keys` attribute and the registry, while deleting no complexity that callers would otherwise have to reimplement: the switch's four branches pass the deletion test as shared infrastructure, not as a pass-through. The DOM predicates the branches read (`data-bzs-date-picker-day`, `data-bzs-date-picker-period`, `role="menuitem"`) are stable `data-bzs-*` and ARIA contracts already locked by ADR-0036, so the shared module reading them is no more a leak than it reading `data-bzs-anchor`. If a fifth key-mode ever appears, it extends the switch; the registry question may be reopened only when the number of modes or the size of the branches makes the switch itself the friction.
