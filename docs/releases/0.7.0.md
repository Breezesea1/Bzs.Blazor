# Bzs.Blazor 0.7.0

This release settles a question ADR-0003 and ADR-0030 had left open: not how
strong a border is, but whether a container should draw one at all. Depth
already communicates a card, a well, or a grouped shell, so those surfaces stop
painting an edge, and the border budget goes to the four edges that carry
information a fill cannot. Most of the change is invisible to markup and
behaviour — components, parameters, events, and ARIA structure are unchanged —
but the visual system is deliberately different, and one theme API breaks.

## Highlights

- A new rule governs every border in the library (ADR-0037): an edge is drawn to
  convey extent the fill cannot, to delimit a surface detached from the content
  behind it, to divide an already-delimited container, or to report state. A
  surface that merely occupies a depth level relies on its shadow and draws
  nothing. This is why a message card used to look bordered while the buttons
  beside it did not, and why the Demo Catalog's theme switch wore a hairline its
  neighbouring language switcher lacked — same visual role, different owner,
  different answer.
- `BzsMessage` drops its box and keeps only the `0.25rem` severity stripe, which
  is the part a visitor actually reads severity from. `BzsToast` keeps a full
  border because it floats — the two components look alike and now diverge on
  purpose, by rule rather than by accident.
- A second border token, `--bzs-border-subtle` (light `#8b939c`, dark
  `#636d78`), takes over every interior division: grid row and column rules,
  dialog and drawer header and footer splits, dividers, menu separators, the
  date picker's action bar. `--bzs-border` stays reserved for the load-bearing
  edges that must reach 3:1 against all five surface levels. The DataGrid had
  already been softening the strong token locally with five ad-hoc
  `color-mix(in srgb, var(--bzs-border) N%, transparent)` strengths — 78, 72,
  68, 62, 58 percent — and all five collapse into the new token.
- The demo header's theme switch and the catalog's own cards and section splits
  follow the same rule, and every literal `1px` border width in the demo gives
  way to `var(--bzs-border-width)`, so a consumer who thickens borders through
  the theme shape finally moves the demo too.
- Every surface that now relies on depth alone restores a visible edge under
  `forced-colors: active`, where shadows vanish. This closes a pre-existing gap:
  `BzsToggle`'s track had no edge there even before this release, so the switch
  could become invisible in high-contrast mode.

## Public API

- `BzsThemeColors` gains a positional `BorderSubtle` member between `Border`
  and `FocusRing`. As with `Scrim` in 0.5.0, this is a breaking constructor and
  `Deconstruct` change, accepted before 1.0 in favor of a token custom themes
  can actually control. A custom theme compiled against 0.6.0 needs its
  `BzsThemeColors` construction updated; `BzsThemes.Default with { ... }`
  callers are unaffected.
- No component parameter, event, markup, or ARIA change. The theme contrast
  gate in the test suite now asserts `--bzs-border` against all five surface
  levels and pins `--bzs-border-subtle` to stay perceptible yet softer than the
  strong token on each of them.

## Demo

- The Demo Catalog stops owning border decisions altogether: its
  `--demo-border` and `--layout-border` aliases fall out because every edge it
  still draws is an interior division, replaced by `-subtle` aliases.
- The landing, forms, tabs, releases, feedback, layout, and productivity pages
  and the render-mode catalog all move their section splits to the subtle
  token.

## Compatibility

`BzsThemeColors` construction is the only breaking change; see Public API
above. Visually, seven of the eleven committed baselines change, which is the
point of the release: raised cards lose a hard hairline they no longer need.
The four landing baselines are unchanged. Existing consumer CSS that targeted
component borders through override hooks keeps working — no override hook name
changed, and the global tokens only gained a member.

## Publication

Pushing the release commit to `main` starts CI and the dependent GitHub Pages
deployment. After the exact-SHA CI run succeeds, pushing the strict `v0.7.0`
tag starts the guarded NuGet workflow. Publication remains subject to the
protected `nuget-production` environment.
