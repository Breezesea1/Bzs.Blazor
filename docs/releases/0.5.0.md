# Bzs.Blazor 0.5.0

This feature release routes every component surface through the semantic token
system and, per ADR-0030, accepts one documented pre-1.0 breaking change to
`BzsThemeColors` in exchange for a scrim that custom themes can actually
control.

## Highlights

- Every component background, shadow, and border colour now resolves through a
  `--bzs-*` token instead of a literal value, so a single theme change moves
  the whole library. Literal radii survive only where the shape is the point —
  circles, pills, and deliberate corner resets.
- Dialogs, drawers, menus, context menus, popovers, toasts, tooltips, select,
  multi-select, autocomplete, and the date picker's panel and period menu share
  one floating treatment: `--bzs-surface-overlay` with `--bzs-shadow-overlay`
  and `--bzs-radius-overlay`. This retires the tooltip's inverted
  text-as-background treatment and the date picker's stacked raised-plus-overlay
  shadow.
- Modal scrims in the dialog, drawer, and navigation drawer now use a
  per-scheme `--bzs-scrim` token, so dark mode no longer reuses a light-mode
  wash.
- Following ADR-0003's flat-lists rule, option rows and calendar day cells tint
  with `--bzs-surface-inset` on hover instead of lifting on a raised shadow,
  and depth is reserved for the pressed state.
- Consumer-facing override hooks such as `--bzs-app-bar-shadow` and the
  navigation drawer background and directional shadows keep their names but
  fall back to semantic tokens, so existing overrides continue to work.

## Theme And Public API

- Adds `BzsThemeColors.Scrim` as the strongly typed source of the per-scheme
  `--bzs-scrim` token, so a custom theme controls the scrim like any other
  colour.
- Adds the `--bzs-surface-overlay`, `--bzs-shadow-overlay`,
  `--bzs-radius-overlay`, and `--bzs-scrim` semantic tokens to the built-in
  light and dark schemes.
- Reworks component stylesheets to consume the semantic surface tokens instead
  of per-component literal backgrounds, shadows, and borders.

## Demo

- The Demo Catalog's `--demo-*` and `--layout-*` surface, text, border, status,
  shadow, and radius tokens are now aliases of the library semantic tokens, and
  its two divergent purples collapse into one brand accent.
- The Demo only still owns the brand accent, the status `-text` variants the
  library has no counterpart for, and non-colour geometry.
- Because those tokens now derive from `--bzs-*`, the Demo's former re-points
  of `--bzs-canvas`, `--bzs-text`, and friends would have become circular and
  were removed; `--bzs-primary` and `--bzs-focus-ring` continue to demonstrate
  consumer overrides.

## Compatibility

`BzsThemeColors` gains `Scrim` as a new positional record member. This is a
**breaking change** for custom themes that construct `BzsThemeColors` by
position or deconstruct it: every constructor call and `Deconstruct` use site
must pass or accept one additional `string` value. ADR-0030 explicitly accepts
this break before 1.0 in preference to a scrim token that only built-in themes
can reach. Consumers that use the built-in themes or construct
`BzsThemeColors` with named or object-initializer syntax are unaffected. All
other surface work is token-level: existing override hook names keep working,
supported render modes are unchanged, and passive markup remains useful under
Static SSR.

## Publication

Pushing the release commit to `main` starts CI and the dependent GitHub Pages
deployment. After the exact-SHA CI run succeeds, pushing the strict `v0.5.0`
tag starts the guarded NuGet workflow. Publication remains subject to the
protected `nuget-production` environment.
