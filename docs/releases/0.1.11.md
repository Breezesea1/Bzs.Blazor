# Bzs.Blazor 0.1.11

This hardening release strengthens package-consumer coverage, release
provenance, and public API compatibility controls.

## Highlights

- Exercises the packaged `BzsDateInput` JavaScript module through real NuGet
  consumption in Interactive Server, WebAssembly, Auto, and WebAssembly AOT
  release paths.
- Verifies that the package contains the colocated `BzsDateInput.razor.js`
  static web asset before a release can proceed.
- Requires a release tag to point to the current `main` commit and requires a
  successful `main` push CI run for that exact SHA before package verification
  starts.
- Establishes a compiler-enforced public API baseline so accidental additions
  and breaking changes fail the runtime build.
- Seals public component classes and prevents consumers from constructing the
  shared component base classes for inheritance, matching the library's
  composition-first extension contract.

## Breaking Changes

Public component classes can no longer be inherited from, and
`BzsComponentBase` and `BzsInputBase<TValue>` can no longer be constructed by
consumer assemblies. Consumers that previously derived from these types must
switch to wrapping components, render fragments, typed templates, semantic
parameters, additional attributes, CSS variables, or supported interfaces.

This is an intentional breaking change during the package's `0.x` development
phase. Component parameters, events, rendering modes, and normal Razor usage
remain supported.

## Publication

Pushing this release preparation commit to `main` starts CI. After CI succeeds
for that exact commit, pushing the strict `v0.1.11` tag starts the guarded NuGet
workflow. The workflow rejects tags that do not point to the current `main`
commit or whose commit lacks a successful `main` push CI run.
